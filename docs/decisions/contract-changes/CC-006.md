# CC-006 — The `Planner(publish_candidates=…)` seam (not named in CONTRACTS §4.2)

| Field | Value |
|---|---|
| Raised by | the integration owner, from the 11 October report (item 2) |
| Change | `planner/jobs.Planner` takes an optional `publish_candidates(session_id, LocationCandidates)` callback; `main.build_resources` passes a function that copies the set into `sessions.get(session_id).candidates`, so the web layer can render the choice and validate a `/location-choice` POST from the session's own copy (BACKEND-CONTRACT §3). |
| Status | **proposed**; Mats approves. Not accepted by the integration owner. |

## What the reviewer asked to know

**Session ownership.** The planner publishes only into the session whose ID started the
job; the candidate IDs are random 16-byte tokens, and `choose_location` checks that the
candidate belongs to the calling session's held set, so a candidate ID from another
session is `NotFound` (indistinguishable from an unknown ID, CONTRACTS §3). The web layer
additionally checks the session's own copy (`Session.live_candidate`) before calling.

**Expiry.** Both copies carry the same `expires_at` (10 min, `CANDIDATES_TTL`). The
planner refuses an expired set in `choose_location` and drops it in `sweep`; the web
layer refuses it in `live_candidate`. A consumed candidate lives on until its job's
`retain_until`. If the session has already expired when the job publishes,
`sessions.get` returns `None` and nothing is published; the planner's copy expires by TTL.

**Duplicate handling.** One set per session: a new ambiguous search replaces the older
set in both copies (`_hold_candidates` overwrites; the session attribute is reassigned).
Choosing the same candidate twice returns the same job (`joined=True`); a repeat POST of
a consumed candidate is redirected to that job's page by the route.

**Two side effects worth knowing.** (1) `sessions.get` inside the callback refreshes the
session's idle timer, so publishing extends the session by up to the idle window.
(2) `sessions.get` also runs the store's purge, which can call `on_end` (CC-005) for
*other* expired sessions from inside the planner's job task; if the publishing session
itself were the one expiring at that instant, `forget_session` would cancel the very
task that is publishing, which `_run` handles as a cancelled job (FAILED). Neither is
observed; both are reported, not fixed.

**Exceptions.** An exception in the callback propagates into the job task and is handled
by `Planner._run` as an unexpected failure (FAILED, UNEXPECTED_FAILURE, logged).
