# CC-005 — The `SessionStore(on_end=…)` seam (not named in CONTRACTS §4.2)

| Field | Value |
|---|---|
| Raised by | the integration owner, from the 11 October report (item 2) |
| Change | `web/security.SessionStore` takes an optional `on_end(session_id)` callback; `main._wire` passes `Planner.forget_session`, so a session that expires or is evicted takes the jobs and candidates it owned with it (BACKEND-CONTRACT §2). |
| Status | **accepted** (Mats, 11 October 2026); the raising-hook guard applied the same evening (`SessionStore._end` catches and logs; `tests/web/test_security.py::test_a_raising_end_of_session_hook_does_not_fail_the_request`). |

## What the reviewer asked to know

**Cleanup order.** `SessionStore._end` deletes the session from its own table first, then
calls `on_end`. `Planner.forget_session` then removes every job the session owned
(`_remove`: drop the record and its key, cancel a still-running task, set `done` so a
waiter wakes and gets `NotFound`), then drops the session's candidate set. So by the time
the planner runs, the session is already unreachable through the store; a request that
races the expiry gets 404 from the planner, never a half-removed session.

**Exception handling.** None on either side. `forget_session` does dictionary work and
`task.cancel()` only, none of which raises in practice; but an exception from `on_end`
would propagate out of `SessionStore.get`, `create`, `_purge` or `_evict` and fail the
unrelated request that triggered the purge with a 500. Proposed hardening, not applied:
catch and log inside `_end`. **Applied 11 October with Mats's approval:** `_end`
removes the session first, then calls the hook inside `try`/`except Exception` and logs
the failure; one test covers a raising hook (the request completes, the store goes on
working). The only hook wired today cannot raise, so this is a guard for the seam, not a
bug observed.

The two side effects of the *other* seam (idle refresh and purge-from-the-job-task) are
listed with recommendations in CC-006.

**Repeated cleanup.** Harmless. `forget_session` for an unknown or already-cleaned session
finds nothing to remove; `_remove` on a missing job is a no-op; cancelling a finished
task is a no-op. Calling it twice for the same session is safe.

**Where it is called.** From `_purge` (every `create` and `get`, idle 30 min or absolute
2 h) and from `_evict` (the 500-session bound). Both run inside ordinary request handling
on the single event loop, so there is no concurrency with the planner's own mutation.

## Tests

`tests/planner/test_jobs.py::test_a_session_ending_removes_everything_it_owned` covers the
planner side. The store side (a purge calling the hook, and the hook raising) is not
tested.
