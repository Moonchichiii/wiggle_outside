# CC-004 — `Answers.location_label`, so a "Change answers" resubmission keeps its label

| Field | Value |
|---|---|
| Raised by | the integration owner, from the 11 October report (item 3) |
| Change | `Answers` gains `location_label: str | None = None` (CONTRACTS §2). The form reader sets it from the hidden `location_label` field only when the submission carries coordinates; the workflow uses it for the answers summary instead of "Your location"; the job fingerprint includes it. |
| Status | **proposed**; Mats approves |

## Why

A "Change answers" form carries the earlier geocode label with its coordinates (D46), the
reader validated it (≤ 80 printable characters) and then dropped it, because `Answers` had
no field for it and the planner service takes only `Answers`. The result page then said
"near Your location" instead of "near Växjö, …".

## Alternative not taken

Adding the label to `PlannerService.start_or_join` would widen the §4.2 seam Mats is
reviewing (CC-005, CC-006).

## Packages affected

WP7 (`routes/parsing.py`), WP6 (`plan_outing.py`, `jobs.py`), WP0 (`core/types.py`).

## Tests that change

None yet: a route-level test of the carried label is listed as open in the 11 October
report. Every existing `Answers(...)` construction stays valid (defaulted field).
